# Custom Specialists

Drop your own feature template into `~/.jarvis/specialists/<name>/` and
Jarvis will pick it up alongside the built-ins. User-defined features
take precedence — same name override = your version wins.

## Layout

```
~/.jarvis/specialists/
└── <my-feature>/
    ├── manifest.yaml          # required — same schema as built-in features
    ├── iac/
    │   └── something.tf.tmpl
    ├── python/
    │   └── service.py.tmpl
    └── tests/
        └── test_something.py.tmpl
```

## Minimum viable manifest

```yaml
feature: my-feature
version: 0.1.0
description: |
  What this feature does. One-liner here shows up in /jarvis-add-X help.

inputs:
  required: [region, app_name]

outputs: [my_output_var]

writes_glob: [iac/my-feature/**/*]

files:
  always:
    - { src: iac/something.tf.tmpl, dst: iac/my-feature/something.tf }
```

## What gets substituted

Every `{{SLOT}}` in your `.tmpl` files gets substituted from the context
JSON at render time. Available slots include everything in the context:
`{{REGION}}`, `{{APP_NAME}}`, `{{ACCOUNT_ID}}`, `{{ISO_DATE}}`,
`{{JARVIS_VERSION}}`, plus `{{TEMPLATE_HASH}}` which is computed
automatically (first 12 chars of sha256 of the template file).

## Header convention

Every generated file should start with:

```
# Generated by Jarvis v{{JARVIS_VERSION}} on {{ISO_DATE}}
# feature:my-feature template:<your-template-name>@{{TEMPLATE_HASH}}
# Safe to edit. Jarvis detects edits on /jarvis-upgrade.
```

The header is what lets `/jarvis-upgrade` know it generated the file
and detect whether you've edited it before patching.

## Conflict rules

- Your `writes_glob` must NOT overlap with any built-in feature's
  `writes_glob`. Convergence agent will halt if it does.
- If you really want to override a built-in (replace a template with
  your own version), use the EXACT same feature name as the built-in
  (e.g., `~/.jarvis/specialists/auth/` overrides the built-in auth).
  Your `writes_glob` takes over completely.

## Testing your custom feature

```bash
# Dry-run render
python3 ~/.claude/skills/jarvis/bin/jarvis-render \
  --feature my-feature \
  --context /path/to/context.json \
  --target-dir /tmp/jarvis-test \
  --dry-run

# Real render
python3 ~/.claude/skills/jarvis/bin/jarvis-render \
  --feature my-feature \
  --context /path/to/context.json \
  --target-dir /tmp/jarvis-test
```

## Sharing

If your specialist is genuinely useful to other Jarvis users, consider
upstreaming it via a PR to `templates/features/` (see CONTRIBUTING.md).
The "incident-derived default" issue template is the right shape for
new specialists.

For team-internal specialists that shouldn't be public: store them in
a private git repo and use `jarvis-brain-sync` to distribute across
your team's laptops.
