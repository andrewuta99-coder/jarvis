# /jarvis upgrade — one-command update

This is the user's escape hatch from version drift. New CloudMortgage incidents become new defaults; new AWS services become new templates; security patches arrive without ceremony.

## Preamble

```bash
JARVIS_DIR="${JARVIS_DIR:-$HOME/.claude/skills/jarvis}"
CURRENT=$(cat "$JARVIS_DIR/VERSION" 2>/dev/null | tr -d '[:space:]')
echo "JARVIS_CURRENT: $CURRENT"

# Fetch latest
( cd "$JARVIS_DIR" && git fetch origin --quiet 2>/dev/null ) || {
  echo "BLOCKED: could not reach origin. Check your network and that $JARVIS_DIR/.git exists."
  exit 1
}

UPSTREAM=$(cd "$JARVIS_DIR" && git show origin/HEAD:VERSION 2>/dev/null | tr -d '[:space:]')
echo "JARVIS_UPSTREAM: $UPSTREAM"

if [ "$CURRENT" = "$UPSTREAM" ]; then
  echo "ALREADY_LATEST: yes"
else
  echo "UPGRADE: $CURRENT -> $UPSTREAM"
fi
```

## Step 1: Already latest?

If `ALREADY_LATEST: yes`, tell the user and exit:

> You're on Jarvis v{current}, which is the latest. Nothing to do.

## Step 2: Show the changelog

```bash
cd "$JARVIS_DIR"
git log --oneline "${CURRENT}..origin/HEAD" 2>/dev/null | head -30
```

Tell the user:

> Jarvis v{upstream} is available. Here's what's changed since v{current}:
> {changelog}
>
> Proceed with upgrade?

## Step 3: Pull + rebuild

If approved:

```bash
cd "$JARVIS_DIR"
git pull --ff-only origin HEAD

# Rebuild binaries if bun is available
if command -v bun >/dev/null 2>&1; then
  bun install --silent 2>/dev/null || true
  bun run build 2>/dev/null || true
fi

# Re-run setup to refresh symlinks
./setup --quiet || true

NEW_VERSION=$(cat VERSION | tr -d '[:space:]')
echo "UPGRADED_TO: $NEW_VERSION"
```

## Step 4: Template migration check

If the user has an active Jarvis project in the current directory (`.jarvis/profile.json` exists), check if any templates the project uses have improved:

```bash
if [ -d ".jarvis" ] && [ -f ".jarvis/profile.json" ]; then
  echo "ACTIVE_PROJECT: yes"
  # Read which features are installed in this project
  FEATURES=$(cat .jarvis/profile.json | python3 -c 'import sys,json;d=json.load(sys.stdin);print(" ".join(d.get("features",[])))' 2>/dev/null)
  echo "INSTALLED_FEATURES: $FEATURES"
fi
```

If `ACTIVE_PROJECT: yes`, for each installed feature compare the template version baked into the user's generated files against the new template version in `$JARVIS_DIR/templates/features/<feature>/manifest.yaml`.

Files in the user's repo have a generated header like:

```hcl
# Generated by Jarvis v0.4.0 - feature:auth template:auth.iam@2026-06-01
# Safe to edit. Jarvis detects edits and asks before overwriting.
```

For each file:
1. Extract the template hash from the header.
2. Compare the current file's content hash to the original template hash. If they match, the user hasn't edited it.
3. If unedited AND the upstream template hash differs, flag it as eligible for auto-patch.
4. If user-edited, skip silently (their customization wins).

Report to user:

> Template changes that affect your project:
>
>   - SES feature: new VPC endpoint pattern (recommended — prevents connect-timeouts)
>   - Auth feature: HMAC secret now loaded from Secrets Manager (recommended — was env var)
>
> Apply changes?
>   A) Yes, generate a migration PR I can review
>   B) Yes, apply directly to my Terraform
>   C) Show me the diff first
>   D) Skip — I'll stay on the old patterns

## Step 5: Apply migrations (if approved)

If A (PR mode):
- Create a new git branch: `jarvis-upgrade-<old>-to-<new>`
- Apply template patches to the eligible files
- Open a PR with a clear description of what changed and why

If B (direct mode):
- Apply patches to the eligible files in the working tree
- Don't commit — let the user review with `git diff`

If C (diff mode):
- Print the diffs to stdout
- Ask again at the end

If D:
- Skip migration entirely

## Step 6: Completion report

Report `DONE` with:
- Old version, new version
- Number of template files migrated (or skipped because user-edited)
- Recommended next: `/jarvis-doctor` to verify the stack still passes

## Auto-upgrade mode

If the user has set `jarvis-config set auto_upgrade true`:

Every skill's preamble runs `jarvis-update-check`. If a new version is available, the upgrade runs silently in the background before the skill executes. Throttled to once per hour. Template migrations are NEVER auto-applied — always require user confirmation.

This matches gstack's pattern: silent CLI upgrade, explicit Terraform migration.
