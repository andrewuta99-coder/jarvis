# Contributing to Jarvis

Thanks for considering it. Jarvis is open source because the production
defaults baked in are too valuable to keep private. Every contribution
that adds an incident-prevention default to the templates is the highest-
leverage thing you can do.

## Quick-start

```bash
git clone https://github.com/andrewuta99-coder/jarvis.git
cd jarvis
./setup --host claude          # or --host codex / cursor / openclaw
./test/run_tests.sh             # 19 tests, stdlib only, runs in <1s
```

That's it. No `npm install`, no Bun required for v1 (it's a dev dep
for compiled binaries that ship in v2).

## What we accept

In rough order of "most welcome":

1. **New incident-derived defaults.** You found a production gotcha that
   should be a Jarvis default. Add it to the relevant template, document
   why in a `# <date> incident:` comment. Examples: a missing VPC endpoint,
   a forgotten IAM permission, a security-group rule that bit you.
2. **New starter manifests.** Got a stack pattern that isn't covered?
   Submit `templates/starters/<name>/manifest.yaml` per the schema in
   existing starters. CI smoke-renders to verify.
3. **New feature templates.** `templates/features/<name>/manifest.yaml`
   + template files. Each template file MUST carry the standard header
   (`# Generated by Jarvis v{{JARVIS_VERSION}} on {{ISO_DATE}}`).
4. **Bug fixes in `bin/*` scripts.** Renderer, orchestrator, doctor —
   anything reproducible. Tests required.
5. **Host adapters.** New AI agent host? Add `hosts/<name>.ts` per the
   `HostConfig` interface.
6. **Docs.** README improvements, troubleshooting entries, architecture
   clarifications. PRs welcome.

## What we don't accept

- **Cosmetic-only refactors.** Renames, formatting, "cleaner" abstractions
  with no behavior change. Maintenance burden > value.
- **Multi-cloud refactors.** AWS-only is intentional through v2. v3 is
  the multi-cloud conversation.
- **New abstractions over Terraform.** No DSL, no Pulumi adapter, no
  "wrap terraform with a friendlier API" — that's AWS Amplify's mistake.
- **Heavyweight dependencies.** Anything that adds > 5MB to a fresh
  install needs a strong justification.
- **AI-generated PR bodies that don't reference real verified behavior.**
  CI catches these; reviewers will too.

## PR checklist

Before opening:

- [ ] `./test/run_tests.sh` passes (19/19)
- [ ] For new templates: smoke render works
  ```bash
  python3 bin/jarvis-render --feature <name> \
    --context test/fixtures/sample-context.json \
    --target-dir /tmp/jarvis-smoke --dry-run
  ```
- [ ] For new features: `manifest.yaml` declares `inputs`, `outputs`,
  `writes_glob` — and the writes_glob does NOT overlap with any other
  feature's writes_glob
- [ ] For Terraform templates: `terraform fmt -check` passes
- [ ] For Python templates: `python3 -m py_compile <file>` (or `ruff check .`)
- [ ] CHANGELOG.md entry under "Unreleased"

PR title format: `feat(<area>): <one-line>` or `fix(<area>): <one-line>`.
Areas: `feature/<name>`, `bin`, `setup`, `docs`, `tests`, `ci`.

## Architecture-decision PRs

If your change touches:
- The agent constellation shape (phases, parallelism)
- The renderer / orchestrator / hash-detection
- Cross-feature contracts
- Security defaults

Open a GitHub Discussion FIRST with a short design note. We don't want
to merge structural changes without alignment, and we don't want you to
spend a weekend on something we'd then ask to revert.

## Templates: the contract

Every file you put under `templates/features/<name>/` MUST be a `.tmpl`
file with the standard header (substituted at render time):

```hcl
# Generated by Jarvis v{{JARVIS_VERSION}} on {{ISO_DATE}}
# feature:<name> template:<file-stem>@{{TEMPLATE_HASH}}
# Safe to edit. Jarvis detects edits on /jarvis-upgrade.
```

The `{{TEMPLATE_HASH}}` is computed automatically by the renderer.
You don't fill it in; the renderer does.

## Local testing against a real AWS sandbox

Don't push code that touches IAM / VPC / Secrets without testing on a
real account at least once. We pay for the lesson up front:

```bash
# Set up an isolated sub-account, ideally with a $100 budget alarm
aws configure --profile jarvis-test
export AWS_PROFILE=jarvis-test

# Render to a temp dir, terraform init/plan only (NO APPLY in tests)
mkdir /tmp/jarvis-pr-test && cd /tmp/jarvis-pr-test
python3 ~/jarvis/bin/jarvis-render --feature <yours> \
  --context ~/jarvis/test/fixtures/sample-context.json \
  --target-dir .

cd iac/<module>
terraform init -backend=false
terraform validate
terraform plan -out=tfplan      # inspect, don't apply
```

If your change passes `validate` + `plan` shows reasonable resources,
that's enough for the PR.

## Code of conduct

Be kind. Disagree on the technical substance, not the person. The bar
for review comments is "would I want to receive this on my PR?"

## Voice for docs and skill prose

- Lead with the point. Say what it does, why it matters, what changes
  for the builder.
- Be concrete. File names, services, dollar amounts.
- Tie technical choices to user outcomes.
- Never corporate, academic, or PR voice.
- Real incidents are the gold. Document them with dates and consequences.
